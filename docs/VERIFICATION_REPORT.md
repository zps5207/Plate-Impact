# Independent verification report — embedded-element mesher toolchain

Scope, rules, and test plan: `VERIFICATION_GOAL.md` (repo root). Commit under test: `9176486` on branch `mesher-v0.1`. This report covers T0–T1 (fully run, locally, independently of the mesher's own tests) and marks T2/T3 (Abaqus on ROAR) **blocked** — see §3 and §9. Bug details: `docs/BUGS.md`.

## 1. Executive summary

**Verdict: the mesher is a working prototype for the single case it was built and tested against (flat, axis-aligned, rectangular, square-in-plane plates with 0/90 truss fibers) but is not correctness-verified for the general cases the goal specification lists.** Of 111 independent checks run across T0/T1, 72 passed and 39 failed; the failures are concentrated in exactly the areas the project's own `docs/PROGRESS.md` had marked done but under-tested: instance transforms, non-square/curved layups, symmetry-BC recognition, the beam fiber type, and Abaqus-format edge cases (continuation lines, `*Include`).

Three biggest issues:
1. **The mesher's `output.inp` is not valid Abaqus input for the common case** (BUG-006, upgraded to blocker and directly confirmed against real Abaqus 2024 on ROAR this session) — whenever the source deck already has a complete `*Assembly ... *End Assembly` (and/or a `*Step`), the entire appended fiber block lands after it, which Abaqus rejects outright (`*NODE ... misplaced`). Every user-facing deliverable of the tool (the patched deck) fails to load in Abaqus for any realistic input.
2. **Instance placement is wrong whenever an instance has both translation and rotation** (BUG-003) — every embedded structure built from a rotated-and-translated instance (the normal case for anything but a single part at the origin) gets the fibers meshed onto the wrong geometry, because the *host mesh itself* is transformed correctly by Abaqus at solve time but the mesher's own fiber placement (which reads `d.instance_nodes(instance)`) uses the same buggy transform to decide where fibers go.
3. **The beam fiber type is unusable with the default 0/90 layup** (BUG-002): the single shared `*Beam Section` normal is parallel to half the fibers' axes, which Abaqus will reject.

Runner-up, and the one piece of genuinely good news: once BUG-006's placement defect is worked around (for testing purposes only — the mesher source was not modified), the **core mechanics are sound** for well-posed flat and cylindrical-shell geometries — 19/19 single-host Explicit mechanics cases, a cantilever, and 5/6 refinement-sensitivity cases ran to completion on real Abaqus with energy balance closing to <0.001% (§4). Curved layups remain a separate, smaller-in-scope gap (the goal's cylindrical shell, spherical shell, varying-thickness plate requirement is far less built than `docs/PROGRESS.md` claims: no CLI/`mesh_*` entry point for any curved case, the one Python-API generator that exists produces only straight axial fibers — no hoop layer, no 0/90 alternation, contrary to its own "t0"/"t90" direction labels — and no spherical-shell or varying-thickness generator at all).

T2 (Abaqus datacheck) and T3 (Abaqus/Explicit mechanics, including the redundancy baseline the VUEL correction will be judged against) **were run** on ROAR (Abaqus 2024) after the user supplied live SSH access mid-session. The headline result from actually running them: **the mesher's own, unmodified `output.inp` is rejected by real Abaqus** whenever the source deck already has a complete assembly (BUG-006, confirmed directly, not inferred) — every one of 6 `*_asis` (raw mesher output) decks failed at the keyword-parsing stage, before Abaqus could even evaluate the embedded-element constraint. Once that placement defect is corrected (a harness-side fix, applied only to test copies — the mesher source itself was not touched), the underlying mechanics work for the well-posed flat and cylindrical-shell cases: 19/19 single-host mechanics runs, a 10×2×2 cantilever, and 5/6 mesh-refinement sensitivity cases completed successfully with energy balance closing to <0.001%. Non-rectangular, face-exact, and skewed-mesh geometries failed with a real, reproducible Abaqus embedding error (`NODE ... DOES NOT LIE IN ANY HOST ELEMENT`), corroborating BUG-009. VUMAT compiles and links cleanly but hits an Abaqus/Explicit limitation with automatic time-step estimation for user materials on 1-D elements that was not resolved this session (T3.VUMAT, blocked). Full detail in §3–§4.

**Reading these numbers:** the uncorrected plain Abaqus embedded element adds the full fiber stiffness on top of the full (uncorrected) host stiffness, with no volume-fraction reduction of the host's own contribution — exactly the redundancy the goal's VUEL correction (§7, tracked separately) is meant to remove. With this run's material choice (E_fiber = 230000, E_matrix = 3500, a 66× stiffness ratio, chosen to make the redundancy visible), the internal energy for a given imposed displacement is 20–27× higher with fibers than without, at φ≈0.58–0.79. **These ALLIE/ALLIE_control ratios are this run's redundancy baseline** — the number the VUEL correction should later be judged against (a correctly volume-fraction-corrected element should show internal energy closer to the fibers-off control, adjusted for the fibers' own genuine stiffness contribution at their true, uncorrected-double-counted volume).

Energy balance closes to well under 0.001% in every case (`|ETOTAL|/ALLIE`), and kinetic energy (`ALLKE`) is 6–10 orders of magnitude below internal energy in every case, confirming the loading rate was quasi-static as intended — both are strong evidence the Explicit solve itself is numerically well-behaved for this simple case; they are not evidence about the mesher's own correctness (that is T1's job).

## 6. Coverage gaps and limitations

- **T2/T3 ran, but several specific measurements the goal asks for were not completed** within this session's remaining time, even though the jobs themselves succeeded: a rule-of-mixtures analytic comparison, a full mass-vs-(matrix×(1−φ)+fiber) table, VUMAT tension/compression/deletion behavior (blocked on an Abaqus/Explicit time-increment-estimation issue for user materials on 1-D elements), the cantilever tip-deflection-vs-beam-theory comparison, a stable-time-increment cross-check against `report.json`'s estimate, and the optional 1-D wave test. See §4's "Not obtained this session" note for the complete list and reasons.
- **VUEL correction track (goal §7) was not started.** The goal says to start it after T0 completes and to delegate it to Codex; this session used all its remaining time on verification (T0/T1 plus, once access arrived, T2/T3) and did not reach the delegation step. `docs/DELEGATION.md`/`tools/run-worker.sh` in the read-only Embedded Elements folder were not inspected for a delegation mechanism.
- Curved-layup CLI: there is no `embmesh visualize`-equivalent entry point for any curved case, so all curved checks in T1.4 had to call the Python API (`embmesh.curved_layup`) directly — this is explicitly allowed by the goal ("black box through their CLI **and output files** where possible") but means curved usage by an actual user (via CLI or the packaged exe) is entirely unverified, separately from the generator's own correctness gaps (BUG list).
- Assembly-level (`*Nset ..., instance=`) set definitions, a very common Abaqus/CAE export pattern, are accepted by the parser without error but stored under the *part's* nsets rather than tracked as assembly-level, and no example deck or test exercises this path — flagged as untested rather than a confirmed bug, since no failure was observed downstream in these test decks (the goal's example decks never use this form).
