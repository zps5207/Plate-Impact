## Hypotheses to test (not conclusions)
- T-018 measured only a small headless window (1280x800). A real desktop window (for example 2560x1440, or a high-DPI display) makes each software render much more expensive, so the async animation loop may block the event loop, starving websocket messages such as the Pause click, and `state.playing` toggling then never runs in time. Check whether `animation_loop` yields to the event loop (is the render/`view_update` awaited or run synchronously?), and how long each tick blocks at large window sizes.
- The playback quality is set to 75 at ratio 0.5 (interactive_ratio=0.5 and interactive_quality=75 are also set on the VtkRemoteView). On a large window that halves the resolution in each axis and may look very soft. Check what the user sees, and whether the quality should adapt to the window size or be configurable (for example `--play-ratio`, `--play-quality`).
- `toggle_play` sets `viewer.is_playing = not state.playing` and then flips `state.playing` in a second place; check for a race or a double toggle (the button handler and the loop both touching state), including after the loop's own end-of-animation/loop handling.
- Anything else in the T-018 changes that could leave the page unresponsive after playing (the `timeBeginPeriod(1)` call, the pacing sleep, quality calls on a render window while an image is being encoded, an exception swallowed in the loop).
