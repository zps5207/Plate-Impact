# T-007
role: drafter
round: 1
goal: Brainstorm the root cause of a confirmed, reproducible bug: a ring of
ghost (C3D8R) elements at the crater boundary that never reach native
`STATUS=0` even though most of their immediate neighbors do, in the
VUEL+ghost coupled deletion scheme (`embmesh/vuelghost.py`,
`uel/VUEL_failure.for`). This is a from-scratch investigation round, not a
continuation of existing code -- be exploratory, propose a mechanism, and
only draft a fix if you're genuinely confident in it; otherwise report the
mechanism clearly and stop.

## Background (read before brainstorming)

This project pairs each host hex element with two coincident elements
sharing the exact same node labels (confirmed by reading
`embmesh/vuelghost.py:convert_to_vuel_ghost`, around line 284-307: the
ghost element is a **new element label** but reuses the **same node
connectivity tuple** as the host -- not a duplicate/tied node set, the
elements are truly node-coincident, so VU1 and ghost see identical
kinematics by construction):

- **VU1** (the `*User Element`, `uel/VUEL_failure.for`): a self-contained
  elastic-plastic hex with its own homegrown failure criteria
  (engineering-strain `EPS_FAIL` and Jacobian-collapse `JAC_FAIL`, see
  lines ~920-937). On failure it sets `svars(KBLOCK,49)=1.0` and prints
  `*** VUEL_FAILURE (...): elem = <jElem(KBLOCK)> ...` to stdout. Abaqus
  cannot natively delete/convert-to-SPH a `*User Element`
  ([[vuel-failure-criterion-finding]]), so VU1 failure alone produces no
  visible hole.
- **Ghost** (a real native `C3D8R`, cloned material with `*Damage
  Initiation, criterion=DUCTILE` and `*Damage Evolution, type=DISPLACEMENT`,
  scaled by `--ghost-scale`): a normal Abaqus element that CAN natively
  delete. Its job is to visually track VU1's failure closely enough that
  deletion looks synchronized with the VU1's own physics.
- Stage 6 round 4 (see [[vuel-plastic-failure-project]]) measured these two
  as synchronized to about one field-output sampling interval (~1e-7s)
  **in the general case**, with 396-398 deletions matching 1:1.

## What's new and confirmed broken

Running the current (T-004 fiber-segmentation + T-006 volume-correction)
code on the full `Flat.inp` deck (ROAR job 56218897, COMPLETED, 807 VU1
failure/degradation stdout events), the user visually spotted ghost
elements that don't delete and the ball visually passing through them. I
(Claude, Hub) confirmed this is real, not a rendering artifact, using the
ODB's own `STATUS` field directly (not the render):

**`diagnose_bands.json`** (in this folder) bands ghost elements by radial
distance from the impact point at the final frame:

```
r=0.000-0.001: 10 elements, 10 deleted, 0 still present
r=0.001-0.002: 20 elements, 20 deleted, 0 still present
r=0.002-0.004: 100 elements, 100 deleted, 0 still present
r=0.004-0.005: 70 elements, 69 deleted, 1 still present
r=0.005-0.006: 88 elements, 82 deleted, 6 still present
r=0.006-0.008: 232 elements, 185 deleted, 47 still present
r=0.008-0.010: 282 elements, 168 deleted, 114 still present
```

The crater core (r <= 0.004) deletes perfectly cleanly. Deletion gets
patchy specifically at the crater's rim/transition zone. I then ran an
"island" check (`diagnose_central_elements2.py`, same file): for every
still-present ghost element within r <= 0.010, count how many of its
nearby neighbors (within ~1.6x estimated element pitch) are already
deleted. **48 elements qualify as true islands** -- still-present ghost
elements with >=60% of their nearby neighbors already dead. Example:
element 39117, centroid near the crater rim, 119 of 157 neighbors already
deleted, itself never reaches STATUS=0. These islands span multiple
through-thickness depths (z from -0.0155 to -0.0175 out of the plate's
-0.02 to -0.01 range), so it is not confined to one ply/layer. Full island
list and per-band data: `diagnose_bands.json` in this folder.

## What you do NOT have, and must account for

**There is no VU1 field output.** I checked `output.inp`: the deck
requests `*Element Output, elset=EMBMESH_GHOST_DIAGNOSTICS` with `S, LE,
PEEQ, SDEG, STATUS` (the ghost's own native fields) but nothing requests
SDV output on `EMBMESH_VUEL_HOST` (the VU1 elset). So **you cannot
directly read `svars(KBLOCK,49)` (VU1's own failure flag) per element from
the existing ODB** -- only the ghost's native state is queryable that way.
The only other signal for VU1 failure is the `*** VUEL_FAILURE` stdout
log, and that log has a caveat: see below.

**The stdout failure log may have scrambled element labels.** I found
`*** VUEL_FAILURE (ENG STRAIN): elem = 31200 ...` in `flat_t006.stdout` --
but VU1 elements are labeled 1-24000 only (confirmed directly from
`output.inp`'s `*Element, type=VU1` block). 31200 = 7200 + 24000, i.e. it
falls exactly in the GHOST label range (ghost = host_label + 24000,
confirmed: `*Element, type=C3D8R, elset=EMBMESH_GHOST_HOST` spans
24001-48000). This is the same class of bug as the Fortran
list-directed-`WRITE(*,*)`-wraps-across-physical-lines issue found and
fixed in T-006's ROAR checker, but here it looks like actual
cross-call/cross-thread interleaving of `WRITE(*,*)` output (Abaqus/Explicit
can parallelize element-block operations across OpenMP threads even under
a single-rank submission), not just line-wrapping. **Treat the stdout
failure log as unreliable for per-element auditing.** This probably does
NOT corrupt the actual physics -- `svars(KBLOCK,*)` writes are indexed by
`KBLOCK`, which should be thread-local/private per Abaqus's own vectorized
block contract -- but verify this assumption rather than taking my word
for it, since it's exactly the kind of thing this project's rules say not
to guess about.

## Confirmed reproducible on a second, independent run

Added after the original brief: a second ROAR run (job 56220096, ball
moved from 0.05m to 0.01m standoff, fiber gap reduced from 0.001 to
0.0002 -- denser fibers, earlier/longer impact dwell, 1532 VU1
failure/degradation stdout events vs. the first run's 807) reproduces the
same island pattern: core (r<=0.005m) deletes 100% cleanly, rim
(r=0.006-0.010m) patchy, **52 islands** this time (vs. 48 in the first
run). See `diagnose_bands_b.json` in this folder (same script, second
ODB). This rules out "fluke of one specific run" -- the mechanism is
robust across two different ball-approach/fiber-density configurations,
which should narrow your hypothesis space in point 3 below (ring-shaped,
not random, and not sensitive to the fiber density change).

## What to brainstorm

1. **Does VU1 actually fail for the 48 island elements' hosts?** You
   can't get a clean answer from the current ODB/stdout (see above). Work
   out the cleanest way to find out: e.g., a minimal deck-generation patch
   that adds `*Element Output, elset=EMBMESH_VUEL_HOST` requesting SDV
   (at least SDV49, maybe SDV106/107 too) so a follow-up ROAR run can
   directly cross-reference VU1's own failure state against ghost STATUS,
   per element. If you propose this, keep it minimal and consistent with
   how the existing `GHOST_DIAGNOSTIC_VARIABLES` field-output request is
   wired in `embmesh/vuelghost.py` (grep for `*Output, field` there).
2. **If VU1 did fail but the ghost's native criterion didn't trigger,
   why might that be, specifically at the crater rim and not the core?**
   The ghost's `*Damage Initiation, criterion=DUCTILE` table currently has
   exactly one row (triaxiality=0, rate=0 -- confirmed: the override
   mechanism in `vuelghost.py` just replaces `values[0]` on the existing
   single-row table, see `_scaled_ghost_material`), so Abaqus should
   extrapolate that single threshold flat regardless of actual stress
   triaxiality at a given element -- meaning a simple "rim loading is more
   multiaxial, so native criterion needs more strain" story may not
   actually apply given this table structure. Check this before
   proposing it as the mechanism. Consider alternatives: numerical
   (element distortion/hourglassing at the rim suppressing the ghost's own
   PEEQ accumulation independent of VU1's measure), geometric (rim
   elements under more shear than tension, and VU1's own `EPS_FAIL` is a
   MAX of three *normal* engineering strains -- so VU1 could trip on a
   shear-dominated state the ghost's isotropic ductile criterion reads
   differently), or something else you find by actually reading both
   criteria's math side by side.
3. **Why does this look like a geometric "ring" around the crater rather
   than scattered randomly?** Is there something about the transition
   between actively-failing and not-yet-failing regions (a stress/strain
   gradient, a wave-propagation front, a boundary between where
   `COMP_RESIDUAL_FRAC`/degradation-ramp logic is active vs not) that
   would naturally produce a ring of near-miss elements, rather than a
   uniform probability of "stuck" elements everywhere?
4. Is "decoupled from their hosts" (the user's phrasing) literally
   possible given VU1 and ghost share the same node labels? I don't think
   so geometrically (shared nodes can't kinematically diverge), but
   confirm or refute this plainly -- maybe there's a sense in which
   their *internal states* desync even though their *displacements*
   can't, and that's what "decoupled" really means here.
