# T-005
role: drafter
round: 1
goal: Brainstorm, then draft, a way to apply the VUEL fiber/host
volume-fraction correction to the host element's **volume** during mesher
preprocessing (reading the mesher's own `fiber_volume.csv`), instead of
Stage 7's already-shipped runtime approach of scaling the host material's
stiffness constants inside the VUEL. This is a from-scratch brainstorm +
first draft, not a continuation of existing code -- be exploratory in the
brainstorm section, concrete in the draft.

## Background (read before brainstorming)

[[vuel-plastic-failure-project]] Stage 7 (committed, shipped, commit
`0cc1e8f` on branch `vuel-plastic-failure`) already fixed the "embedded
fiber double-counts stiffness against the host" problem
(`docs/VERIFICATION_REPORT.md` section 4: 20-27x too-high internal energy
at Vf~0.58-0.79) by scaling the host's elastic/plastic material constants
(`ALAMBDA`, `AMU`, `BULK_MODULUS`, `CMAT`, `SIGY0`, `HMOD`) per element
inside `uel/VUEL_failure.for`, by `eta = 1 - Vf`, at runtime, using
`svars(KBLOCK,107) = FIBER_VOL_FRAC` (already populated per element today
via `*Initial Conditions, TYPE=SOLUTION` from the mesher's
`fiber_volume.csv` -- this data path already exists and works, nothing
to change there). See `agents/refiner/inbox/VUEL_VOLUME_FRACTION_
CORRECTION_2026-10-07.md` for the full algebra Codex implemented.

**The problem with that approach, and why we want a second one:**
scaling stiffness directly means `CWAVE`/`dtimeStable` (the wave-speed-
derived stable time increment) had to be deliberately left *unscaled* as
a conservative approximation -- Stage 7 did not, and could not cleanly,
correct wave speed, because wave speed is derived from the *material*
constants it was scaling. The user wants a mechanism where density and
the true elastic moduli are left alone, and instead the element's
**volume** (as used in force/stiffness integration and the lumped mass
calculation) is what gets corrected by `eta`. If volume -- not material
stiffness -- carries the correction, wave speed
(`sqrt((lambda+2*mu)/rho)`) and the stable time increment derived from it
should come out exactly right with no approximation, since neither
depends on volume.

## What to brainstorm first (write this up before drafting code)

1. How does `uel/VUEL_failure.for` currently compute/use element volume
   internally -- is it an explicit Jacobian-determinant x quadrature-
   weight integral already separable from the stiffness calculation, or
   is it implicit/fused into other steps? Read the subroutine fully
   before answering.
2. If element volume were scaled by `eta_k` at the point it's used for
   (a) internal-force/stiffness integration and (b) the lumped mass
   matrix (`AMASS` or equivalent) -- trace through what else in the
   subroutine implicitly assumes volume is the element's true geometric
   volume (e.g. does anything else derive density-times-volume = mass
   and then reuse that mass elsewhere in a way that would become
   inconsistent?).
3. Compare this against Stage 7's approach: does scaling volume instead
   of stiffness still cancel out of the radial-return algebra the way
   Stage 7's `eta` canceled out of `DGAMMA` (so `PEEQ`/yield strain stay
   correct)? Work this out algebraically, don't guess.
4. Does the correction have to be read via the same `svars(107) =
   FIBER_VOL_FRAC` -> `*Initial Conditions, TYPE=SOLUTION` path Stage 7
   already uses (recommended -- reuse the existing, working data path),
   or does your analysis suggest it needs to apply even earlier, in the
   mesher's own geometry/deck generation (before the VUEL ever runs)?
   State your reasoning plainly; this is the key open design question
   the human hasn't resolved yet.
5. Flag any case where correcting volume (rather than stiffness) could
   break something structural -- e.g. if other code reads the host
   element's nodal coordinates and assumes they imply a specific
   physical volume (shared faces/nodes with neighboring elements can't
   be moved to "shrink" volume without breaking mesh connectivity, so
   this almost certainly has to be a VUEL-internal integration-volume
   scale factor, not an actual geometric change to node positions --
   confirm or refute this assumption explicitly).
