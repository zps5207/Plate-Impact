# T-027
role: drafter

goal: Make `--curved stacked` work on a REAL CAE-exported curved deck (the original `Meshing/Flat-curved-p0/Flatv2_curved.inp`) by removing its hidden assumption about hex node ordering. The Hub ran the mesher on that deck and it refused with `embmesh: stacked layup: face translation mismatch 0.00171493 exceeds 0.0001055 m`.

## What the Hub found (verified, do not redo)
`embmesh/stacked.py` (in the project now, copied from your T-026 outbox) assumes that for EVERY hex, nodes 1-4 (indices 0..3) form one stack-direction face and nodes 5-8 (indices 4..7) the opposite face. It computes `delta = hexes[:,4:].mean(1) - hexes[:,:4].mean(1)` and a per-hex congruence mismatch from that pairing. Real CAE meshes do not guarantee this. On `Flatv2_curved.inp` (24,000 C3D8R) the local thickness axis from `embmesh.geometry.hex_thickness_axis` is zeta (nodes 1-4 vs 5-8) for only 5,146 hexes; it is xi for 7,746 and eta for 11,108. 10,000 hexes have |dz| < 0.5 mm for the "5-8 minus 1-4" vector, i.e. that pairing is an in-plane direction there. So the mismatch of 1.7 mm is the mesher misreading the hex orientation, not a real geometry problem. The earlier tests passed because (a) the flat Flatv2 goes through the legacy `regular_planes` path, which bypasses this, and (b) the T-023/T-024 `curved_hostonly.inp` was rebuilt by script with consistent node ordering. The original Flatv2 deck is therefore the first real test of the curved path and it fails.

Evidence script (Hub's): `hex_thickness_axis` over all elements gives {1: 11108, 0: 7746, 2: 5146}.

## What to change (deliver under outbox/T-027/embmesh/ and outbox/T-027/tests/, mirroring the project; the Hub copies them in)
1. In `embmesh/stacked.py`, determine the stack-direction face pair PER HEX from geometry, not from local node indices: once the world stack axis is known (from the host region's overall layer direction, e.g. the median over hexes of the local axis whose face-pair vector aligns best with it, or `thickness_axis` if given), for each hex pick the local axis whose lo->hi vector has the largest |component| along the stack axis, orient so "bottom" is the lower stack coordinate, and build the bottom face, top face and the CORRESPONDING node pairs (node at xi=-1 pairs with the node at xi=+1 that shares its other two local coordinates; do NOT reuse the `_HEX_FACE_PAIRS` index lists from `embmesh/geometry.py` for node pairing, they list faces in different order; use the sign table in `hex_volume`/`inverse_hex`). All later logic that currently reads `hexes[:, :4]` / `hexes[:, 4:]` (the congruence mismatch, `delta`, `step_vec`, choosing reference-surface faces/bottom boundary faces, edge lengths for the tolerance, the surface function f(x,y)) must use the oriented faces instead.
2. Keep behavior for decks that already work: `curved_hostonly.inp` and the flat Flatv2 legacy path must produce byte-identical `output.inp` to the outputs you already produced (T-025 `curved_stacked/` from Codex and your T-026 `flat_stacked/` / `flat_plain/`).
