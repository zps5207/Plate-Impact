## Background (read before touching anything)

This project builds an Abaqus/CAE `noGUI=` visualization script that
renders PNG frame sequences from a large (5.2GB) ODB
(`flat_vg_r4.odb`) showing a VUEL+ghost-element plate-impact simulation.
It already has three working render passes (STATUS, displacement
magnitude, and -- until this round -- a translucent-shaded fiber pass)
that were verified on ROAR and are already assembled into MP4s. The
STATUS and displacement passes are done and correct; **do not touch
them.**

The remaining problem is specifically the fiber pass
(`set_fiber_display()` in the file below): the embedded fiber network
needs to be visible *through* the host material. A translucent-shaded
host (round 3, confirmed working on real Abaqus) wasn't see-through
enough -- it read as a solid grey plate. Round 4 (the version in your
inbox copy) switched the host to wireframe-only by putting the host and
the fiber+ball content in two separate, simultaneously-visible Abaqus
session display groups with different render styles (wireframe vs.
shaded) -- but it crashes on real Abaqus/Explicit 2024 with:

```
AttributeError: 'DGCommonOptions' object has no attribute 'setValues'
File "render_ghost_failure.py", line 380, in set_fiber_display
    host_instance.odbDisplayOptions.commonOptions.setValues(
```

So `DisplayGroupInstance.odbDisplayOptions.commonOptions` (obtained via
`viewport.odbDisplay.displayGroupInstances[name]`) does **not** support
`.setValues(...)` the way `viewport.odbDisplay.commonOptions` does
(that one, used earlier in the same function to seed shared defaults,
works fine). Whatever the actual Abaqus 2024 mechanism is for giving two
simultaneously-visible display groups in one viewport different render
styles (one wireframe, one shaded), it isn't this. You'll need to find
the real API -- consult Abaqus 2024's scripting reference for
`DisplayGroupInstance`, `OdbDisplayOptions` (the per-instance vs.
per-viewport objects are genuinely different classes with different
attributes), and `DGCommonOptions`, since the previous two attempts both
guessed wrong.

## What "done" actually requires

The fiber pass (`set_fiber_display()`) must, in one viewport, at the same
time:
1. Render the ghost host (`GHOST_ELSET = "EMBMESH_GHOST_DIAGNOSTICS"`) as
   **wireframe/edges-only** -- no filled or shaded host faces, so nothing
   obstructs the fibers behind it.
2. Render the fiber elsets (`EMBMESH_FIBERS_T0`, `EMBMESH_FIBERS_T90`, on
   instance `EMBFIB-1`) **opaque, bright red** (`FIBER_COLOR =
   "#FF0000"`).
3. Render Ball-1 (`BALL_INSTANCE = "BALL-1"`) **opaque, dark gray**
   (`BALL_COLOR = "#606060"`).
4. Keep `FREE` visible edges and `THICK` edge width (so the host's outer
   silhouette and the fiber T3D2 centerlines both stay legible -- this
   was confirmed correct in round 3/4, don't change it).
5. Keep node symbols, node labels, element labels, and face labels
   **OFF** (round 2's fix for the node-marker clutter bug -- do not
   reintroduce `nodeSymbolColor` in any `setColor` call, that's what
   caused it originally).
6. Keep `colorCodeOverride=ON` and make sure no later viewport-level
   `CommonOptions` call runs after the color/style assignments and resets
   them (round 3's bug: a late `colorCodeOverride=OFF` call silently
   wiped every custom color back to Abaqus's flat default green).

If you can't find a way to cleanly give two simultaneous display groups
different render styles, an acceptable fallback is to **drop the
translucent/shaded-host idea entirely and render the whole viewport in
wireframe for this pass**, as long as the fiber and ball leaves still end
up opaque-colored (not just wireframe-colored) via explicit leaf-level
`setColor` calls the way the existing code already does for the fiber and
ball leaves. Say plainly in your RESULT which approach you took and why.
