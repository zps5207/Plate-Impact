## Background

This project builds a self-contained elastic-plastic VUEL (user element)
with homegrown failure, used as the "host" material in an embedded-fiber
plate-impact model (fibers are separate T3D2/B31 elements laid inside the
host hex mesh via Abaqus's `*Embedded Element` constraint). The known
problem: a plain `*Embedded Element` setup double-counts stiffness -- the
host keeps its full modulus AND the embedded fiber adds its own full
stiffness on top, with no volume-fraction reduction of the host's own
contribution. `docs/VERIFICATION_REPORT.md` section 4 has the measured
baseline: with a 66x fiber/matrix stiffness ratio, internal energy for a
given imposed displacement came out 20-27x higher with fibers than
without, at fiber volume fraction (Vf) ~0.58-0.79. The intended fix is a
volume-fraction correction on the host's own stiffness inside the VUEL
(reduce the host's elastic contribution by roughly a function of Vf, so
it isn't double-counted against the fiber's own separately-modeled
stiffness).

**This brief is scoped narrowly to the mechanism, not the final formula.**
Specifically: how does the VUEL efficiently get Vf, and where/how should
it apply a correction, given the code structure below. A follow-up round
will nail down the exact correction formula with the human.

## What already exists (read these, don't re-derive)

1. **The CSV-to-VUEL data path appears to already be solved** --
   verify this claim rather than assuming it, since the brainstorming
   question changes a lot depending on whether it's true:
   - `embmesh/` computes per-host-element fiber volume fraction and
     writes it to `fiber_volume.csv` (existing mesher feature, Stage 6
     `verification/roar/t5/_mesher_out/fiber_volume.csv` is a sample
     output if you want to see the shape of the data).
   - `embmesh/vuelghost.py` (around lines 240-248) writes that per-element
     value straight into the generated Abaqus input deck as
     `*Initial Conditions, TYPE=SOLUTION` targeting state-variable slot
     107 -- i.e. Abaqus itself loads the per-element value into
     `svars(KBLOCK,107)` once, at job start, before the VUEL subroutine
     is ever called. There is no CSV file I/O happening inside the
     Fortran at all.
   - `uel/VUEL_failure.for` already reads it every call: lines 432-433,
     `FIBER_VOL_FRAC = svars(KBLOCK,107)` (guarded by `nsvars .GE. 107`).
     The doc comment at line 179-182 explicitly says this is
     "Observation/bookkeeping only in Stage 6; it does not alter the
     constitutive response" -- confirmed by grep, `FIBER_VOL_FRAC` is
     never used anywhere else in the file.
   - **Question for you:** is `*Initial Conditions, TYPE=SOLUTION` into a
     UEL/VUEL state-variable slot actually the right/only way to get
     per-element data in at job start, or are there better alternatives
     (e.g. via `props`/`jprops`, external database read in
     `UEXTERNALDB`, etc.)? If the existing mechanism is already sound,
     say so plainly rather than proposing a replacement for its own sake.

2. **Per-call structure that matters for where a correction can cheaply
   live** (`uel/VUEL_failure.for`):
   - `props(1:13)` are **not** per-element -- they come from one shared
     `*UEL Property` material block, so `EMOD = props(1)` (line 360) is
     literally the same scalar for every element of this type. A
     per-element correction therefore cannot live in `props`; it has to
     come from something that varies per element, which today is only
     `svars`.
   - The isotropic elasticity matrix `CMAT` (Lame parameters from
     `EMOD`/`ENU`, lines 379-401) is built **once per subroutine call,
     before the per-element loop**, and is shared across every element in
     the current call's block (`nblock` elements, vectorized call -- see
     `DO KBLOCK = 1, nblock` at line 429). It is not currently
     element-specific.
   - There is a dedicated one-time-per-element operation code,
     `jMassCalc` (line 469, "OPERATION CODE: MASS MATRIX CALCULATION"),
     that Abaqus/Explicit calls to build the lumped mass matrix from
     `DENS * ELVOL` in the reference configuration, before the main
     time-stepping begins. The human's working assumption, which you
     should sanity-check rather than take on faith, is that this is a
     legitimate place to also do other one-time per-element setup work
     (like precomputing and caching a per-element correction factor from
     `svars(107)`), since it already runs once per element rather than
     once per increment like `jIntForceAndDtStable` (line 516, the main
     stress/internal-force loop, which runs every explicit increment --
     this test case alone was ~15,051 increments x 24,000 host elements).
   - There are no spare `svars` slots documented beyond 107 (the layout
     at lines 160-182 accounts for all 107); any cached per-element value
     would need either a new slot (bump `nsvars` again, as Stage 6 did
     105->107) or reuse of an existing one if one is provably safe to
     repurpose (unlikely; check before suggesting it).

## What to brainstorm

1. **Confirm or correct** whether the existing `*Initial Conditions,
   TYPE=SOLUTION` -> `svars(107)` path is in fact the efficient way to
   get per-element CSV-derived data into the VUEL, per point 1 above.
2. **Where and when to compute the correction.** Compare at least:
   - computing a per-element correction every call inside
     `jIntForceAndDtStable` (simplest, but re-evaluated every increment
     for every element -- quantify what that actually costs, don't just
     assert it's expensive or cheap);
   - computing it once per element during `jMassCalc` and caching the
     result in a new `svars` slot for reuse in every subsequent
     `jIntForceAndDtStable` call;
   - any other mechanism you think is worth considering (e.g. is there
     a true Abaqus/Explicit "initialization" operation code distinct
     from `jMassCalc` that would be a more correct hook than piggy-
     backing on the mass calculation?).
3. **How the correction would actually get applied to `CMAT`/stress**,
   given `CMAT` today is shared across the whole element block, not
   per-element:
   - rebuilding a per-element `CMAT` from a per-element corrected `EMOD`
     inside the `KBLOCK` loop, vs.
   - keeping the shared `CMAT` and applying a per-element scalar multiply
     to the resulting PK2 stress (mathematically equivalent for linear
     elasticity at fixed Poisson's ratio -- confirm this equivalence
     holds, don't just take it as given) -- and which is actually cheaper
     given Fortran/Abaqus/Explicit vectorized-block call conventions.
4. **Flag, do not resolve, this physics interaction risk:** `SIGY0`
   (yield stress, `props(8)`) is an absolute stress threshold compared
   against stress computed from `CMAT`. If the correction reduces the
   effective elastic stiffness but `SIGY0` is left unscaled, the strain
   at which the material yields shifts -- which could invalidate the
   Stage 1 plasticity calibration (`docs/VUEL_PLASTIC_FAILURE_STAGE1_REPORT_2026-10-01.md`)
   and the Stage 2 engineering-strain failure calibration
   (`docs/VUEL_PLASTIC_FAILURE_STAGE2_REPORT_2026-10-01.md`), both of
   which were calibrated against the *uncorrected* modulus. Lay out the
   options (e.g. scale `SIGY0`/`HMOD` by the same factor to preserve
   yield strain, vs. leave them alone and treat the shift as an
   accepted recalibration cost, vs. something else) with their
   consequences, but do not pick one -- that is a physics decision for
   the human, not an implementation detail.
